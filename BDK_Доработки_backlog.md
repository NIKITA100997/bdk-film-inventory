# БДК — учёт плёнки: доработки по итогам код-ревью

Собрано по итогам сверки репозитория `NIKITA100997/bdk-film-inventory` с ТЗ (`БДК_Проект_учета_пленок.md`). Ниже — всё, что обсуждалось: найденные баги, архитектурные проблемы навигации, новые функции администрирования и открытые вопросы по готовности к полевому запуску.

## 2. Архитектура навигации — объекты, а не действия

Текущая проблема: меню построено вокруг глаголов (отдельная кнопка на каждое действие), а не вокруг объектов (единица плёнки, позиция материала). Из-за этого один и тот же паттерн "скан ID → карточка → форма действия" продублирован четыре раза в разных экранах, а поиск/список остатков реализован параллельно в трёх местах.

### 2.1. Карточка единицы (новая, объединяющая)

Заменяет собой отдельные пункты меню **"Разделить рулон"**, **"Раскрой"**, **"Возврат"**, **"Размещение в ячейку"**, **"Перенести на склад"** (сейчас — `Split.tsx`, `Cut.tsx`, `Return.tsx`, `Place.tsx`, почти идентичные по структуре).

- [x] Один экран: сканирование QR **или** переход из объединённого списка материалов (2.2) → карточка конкретного ID.
- [x] Показывает: материал/цвет/толщина/производитель, текущие ширина/длина, статус, где сейчас (адрес или участок), УПД/паллета, историю (кто и когда с ней что делал).
- [x] Пул действий формируется по текущему статусу единицы:
  - На хранении → Разделить, Переместить (сменить ячейку), Выдать участку, Списать.
  - Выдан участку, цельнолистовые → Раскрой, Вернуть.
  - Выдан участку, окутка/щитовые → Вернуть.
  - Принят без адреса → Разместить (с автопредложением, как сейчас в `Place.tsx`).
- [x] Автоподбор адреса (`suggestLocation`) остаётся тем же вызовом, но встроен в карточку, а не дублируется в трёх разных страницах.
- [x] Старые роуты `/m/split`, `/m/cut`, `/m/return`, `/m/place` — либо редиректят на карточку конкретной единицы, либо удаляются из меню полностью в пользу входа через скан/список. *(удалены; выдача участку из карточки ведёт на `/m/issue` с предзаполнением, донор-предложение — обратно в карточку единицы)*

### 2.2. Материалы — один список вместо трёх

Сейчас параллельно существуют: `Dashboard.tsx` (без фильтров), `Search.tsx` (с фильтрами, но не в том же месте) и список единиц внутри `MaterialCard.tsx` — три разные реализации одного и того же "найти нужный рулон/штрипс".

- [x] Единая таблица с переключателем **"по позициям материала"** (агрегат) / **"по физическим единицам"**.
- [x] Общий набор фильтров: материал, цвет, толщина, производитель, статус, участок, ширина, минимальная длина.
- [x] Фильтр **"класс C, есть донор-кандидат"** — встроенная замена отдельной страницы `CuttingRecommendations.tsx`, которая сейчас изолирована от повседневного потока (донор и так уже всплывает автоматически в `/units/issue`, но отдельная страница рекомендаций требует, чтобы кто-то зашёл туда специально).
- [x] Кнопка **"Пересчитать ABC"** — здесь же, рядом с фильтрами, с датой последнего пересчёта (сейчас есть только на отдельной изолированной странице).
- [x] Клик по строке единицы → карточка единицы (2.1). Клик по строке позиции → карточка материала (агрегат, план/факт, разбивка по ширинам — уже реализовано, не трогаем).

### 2.3. Приёмка партии — сессия вместо одной страницы на рулон

- [x] Одна сессия приёмки на весь УПД, а не отдельный проход формы на каждый рулон.
- [x] Внутри — быстрый повторяющийся цикл: автокомплит материала/цвета/толщины/производителя (с запоминанием предыдущего ввода для рулонов того же цвета), ширина/длина с рулона, кнопка "Следующий" сразу открывает новую строку.
- [x] Автоподбор ячейки на этом же шаге — сейчас `Receive.tsx` не вызывает `suggestLocation` вообще, только опциональное текстовое поле адреса.
- [x] В конце сессии — сводка (сколько рулонов, сколько новых позиций материала создано) и печать всех этикеток одной кнопкой (частично уже есть — "Печать всех этикеток" в `Receive.tsx`, но привязано к одной приёмке одного цвета за раз).

## 3. Администрирование пользователей (отсутствует полностью)

Сейчас нет ни API, ни экрана — есть только `GET /auth/users` (список активных, используется исключительно для выбора участников инвентаризации). Пользователь заводится напрямую в БД.

- [x] `POST /users` — создание (ФИО, логин, временный пароль, роль, участок — если роль "начальник участка").
- [x] `PATCH /users/{id}` — смена роли/участка/статуса активности.
- [x] `POST /users/{id}/reset-password` — сброс пароля.
- [x] Деактивация вместо удаления (чтобы события в журнале не теряли автора).
- [x] Экран в администрировании: список с фильтром по роли → форма создания/редактирования.

## 4. Редактор макета этикетки (новая функция)

Сейчас макет и набор полей жёстко зашиты в `services/labels.py` как HTML-шаблон.

- [x] Список доступных для печати полей — всё из карточки единицы: ID, QR, материал, цвет, толщина, производитель, УПД, паллета, дата приёмки, код у поставщика, родная ширина, статус (цветная полоса), "из рулона №…".
- [x] **Ширина и длина в список по умолчанию не включать** — это принципиальное решение ТЗ (2.2): их отсутствие на бирке даёт всю экономию на переэтикетировании при разделении. Если всё же нужно оставить возможность их добавить — явное предупреждение в интерфейсе конструктора о потере актуальности.
- [x] Настройка порядка полей построчно (сверху вниз, с размером/жирностью шрифта) — не полноценный drag-n-drop холст, а список с сортировкой, этого достаточно для термопечати и надёжнее.
- [x] Физический размер этикетки — тоже параметр, не константа (сейчас 60×90 мм зашито).
- [x] Хранить макет как структуру (список полей + порядок + опции отображения), а не как HTML — `render_label_html` должен стать интерпретатором этой структуры, а не фиксированной функцией.
- [x] Превью и печать тестовой этикетки перед сохранением макета.
- [x] Место в администрировании — отдельный пункт "Макет этикетки", рядом со справочниками.

## 5. Прочие гибкие настройки

- [x] **Число ячеек на полке штрипсового стеллажа** — сейчас захардкожено (`CELLS_PER_STRIP_SHELF = 10` в `placement.py`), хотя по ТЗ должно "зависеть от ширины". Вынести в настройки — общий дефолт или per-стеллаж.
- [x] **Порог "давно не двигалась"** — отдельно от порога минимальной полезной ширины: сколько дней единица может пролежать без движения, прежде чем это станет сигналом на ревизию/инвентаризацию.
- [ ] **Матрица доступа "роль × раздел меню"** — сейчас список ролей на каждый пункт меню зашит в `navConfig.ts` (источник обеих багов из раздела 1). Рассмотреть перенос в администрирование как редактируемую таблицу чекбоксов — тогда подобные ошибки правятся без правки кода. *(отложено вместе с разделом 2 — завязано на ту же структуру навигации)*
- [x] **Шаблон текста сигнала о нехватке** (в разделе "Закупки") — сейчас формат зашит в логику; вынести в настройку по мере роста числа поставщиков/формулировок.

## 6. Открытый вопрос: донор-резка в два шага

Сейчас подтверждение донор-рекомендации — не атомарная операция: `/units/issue` только предлагает донора и логирует событие `Донор_предложен`; оператор вручную вызывает `/units/{id}/split`, а затем повторяет выдачу на результат. Рабочий вариант, но не "одно нажатие", как в макете.

- [ ] Решить: объединять ли в один атомарный вызов (резка + выдача за один шаг), или оставить как есть — два самостоятельных, но связанных действия.
