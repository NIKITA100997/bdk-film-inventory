## 2. Архитектура навигации — объекты, а не действия

Текущая проблема: меню построено вокруг глаголов (отдельная кнопка на каждое действие), а не вокруг объектов (единица плёнки, позиция материала). Из-за этого один и тот же паттерн "скан ID → карточка → форма действия" продублирован четыре раза в разных экранах, а поиск/список остатков реализован параллельно в трёх местах.

### 2.1. Карточка единицы (новая, объединяющая)

Заменяет собой отдельные пункты меню **"Разделить рулон"**, **"Раскрой"**, **"Возврат"**, **"Размещение в ячейку"**, **"Перенести на склад"** (сейчас — `Split.tsx`, `Cut.tsx`, `Return.tsx`, `Place.tsx`, почти идентичные по структуре).

- [x] Один экран: сканирование QR **или** переход из объединённого списка материалов (2.2) → карточка конкретного ID.
- [x] Показывает: материал/цвет/толщина/производитель, текущие ширина/длина, статус, где сейчас (адрес или участок), УПД/паллета, историю (кто и когда с ней что делал).
- [x] Пул действий формируется по текущему статусу единицы:
  - На хранении → Разделить, Переместить (сменить ячейку), Выдать участку, Списать.
  - Выдан участку, цельнолистовые → Раскрой, Вернуть.
  - Выдан участку, окутка/щитовые → Вернуть.
  - Принят без адреса → Разместить (с автопредложением, как сейчас в `Place.tsx`).
- [x] Автоподбор адреса (`suggestLocation`) остаётся тем же вызовом, но встроен в карточку, а не дублируется в трёх разных страницах.
- [x] Старые роуты `/m/split`, `/m/cut`, `/m/return`, `/m/place` — либо редиректят на карточку конкретной единицы, либо удаляются из меню полностью в пользу входа через скан/список. *(удалены; выдача участку из карточки ведёт на `/m/issue` с предзаполнением, донор-предложение — обратно в карточку единицы)*

### 2.2. Материалы — один список вместо трёх

Сейчас параллельно существуют: `Dashboard.tsx` (без фильтров), `Search.tsx` (с фильтрами, но не в том же месте) и список единиц внутри `MaterialCard.tsx` — три разные реализации одного и того же "найти нужный рулон/штрипс".

- [x] Единая таблица с переключателем **"по позициям материала"** (агрегат) / **"по физическим единицам"**.
- [x] Общий набор фильтров: материал, цвет, толщина, производитель, статус, участок, ширина, минимальная длина.
- [x] Фильтр **"класс C, есть донор-кандидат"** — встроенная замена отдельной страницы `CuttingRecommendations.tsx`, которая сейчас изолирована от повседневного потока (донор и так уже всплывает автоматически в `/units/issue`, но отдельная страница рекомендаций требует, чтобы кто-то зашёл туда специально).
- [x] Кнопка **"Пересчитать ABC"** — здесь же, рядом с фильтрами, с датой последнего пересчёта (сейчас есть только на отдельной изолированной странице).
- [x] Клик по строке единицы → карточка единицы (2.1). Клик по строке позиции → карточка материала (агрегат, план/факт, разбивка по ширинам — уже реализовано, не трогаем).

### 2.3. Приёмка партии — сессия вместо одной страницы на рулон

- [x] Одна сессия приёмки на весь УПД, а не отдельный проход формы на каждый рулон.

- [x] В конце сессии — сводка (сколько рулонов, сколько новых позиций материала создано) и печать всех этикеток одной кнопкой (частично уже есть — "Печать всех этикеток" в `Receive.tsx`, но привязано к одной приёмке одного цвета за раз).

## 4. Редактор макета этикетки (новая функция)

Сейчас макет и набор полей жёстко зашиты в `services/labels.py` как HTML-шаблон.

- [x] Список доступных для печати полей — всё из карточки единицы: ID, QR, материал, цвет, толщина, производитель, УПД, паллета, дата приёмки, код у поставщика, родная ширина, статус (цветная полоса), "из рулона №…".

- [x] Хранить макет как структуру (список полей + порядок + опции отображения), а не как HTML — `render_label_html` должен стать интерпретатором этой структуры, а не фиксированной функцией.
- [x] Превью и печать тестовой этикетки перед сохранением макета.
- [x] Место в администрировании — отдельный пункт "Макет этикетки", рядом со справочниками.

## 6. Открытый вопрос: донор-резка в два шага

Сейчас подтверждение донор-рекомендации — не атомарная операция: `/units/issue` только предлагает донора и логирует событие `Донор_предложен`; оператор вручную вызывает `/units/{id}/split`, а затем повторяет выдачу на результат. Рабочий вариант, но не "одно нажатие", как в макете.

- [x] Решено: объединили в один атомарный вызов — `POST /units/issue-donor-atomic` (резка + выдача за один шаг), кнопка «Выдать донора в 1 клик» в `Issue.tsx`.

## 8. Навигация по функциям + гибкая ролевая модель

Раздел 2 закрыл дублирование внутри карточки единицы/материала, но не устранил его источник: навигация всё ещё собрана из двух параллельных деревьев (`mobileBlocks` и `desktopSections`), каждое из которых группирует пункты по роли/участнику, а не по функции. Отсюда конкретное дублирование в `navConfig.ts` прямо сейчас:

- **"Карточка единицы"** — три записи на один и тот же `/m/unit-card`: `m-unit-card-warehouse` (блок "Склад"), `m-unit-card-my-area` (блок "Мой участок"), плюс сам пункт не нужен вовсе как самостоятельный (см. 8.1).
- **"Карточка материала"** — две записи на `/materials`: `m-material-card` (мобильный блок "Общее") и `d-materials` (десктопный раздел "Материалы").
- **"Остатки"** — две записи на `/stock`: `m-stock` и `d-stock`.

Раздел 5 уже отмечал зависимость: пункт "матрица доступа роль×раздел" был отложен именно потому, что завязан на эту же структуру — теперь пересматриваем оба вопроса вместе.

### 8.5. Кнопка "+ Новое" на экране "Остатки"

Раз добавление позиций и единиц не сосредоточено в одном явном месте (позиция создаётся неявно через приёмку, единица — только через приёмку или инвентаризацию), на "Остатках" нужна прямая точка входа с двумя вариантами:

- [x] **"Материал"** — форма создания позиции без физической единицы (материал/цвет/толщина/производитель/код у поставщика/родная ширина — те же поля, что в `MaterialSku`). Пригодится, чтобы завести номенклатуру заранее, до фактической поставки (например, под будущую позицию недельного плана).

## 14. Коррекция: планирование по заказ-нарядам, не по неделям

Original ТЗ (раздел 2, "Ключевое требование") закладывал **недельное планирование цеха** ("Начальник цеха формирует недельный план (м²)") как основной ритм производственного планирования. Пользователь поправил: в реальности работа организована не по календарной неделе, а **по отдельным заказ-нарядам** — печатным документам вида «Наряд-заказ [деталь]» на конкретный заказ/партию, каждый из которых должен превращаться в одно производственное задание (`ProductionTask`) в системе.

Хорошая новость: `ProductionTask` в текущей реализации уже не привязана ни к какой календарной неделе (нет ни поля недели, ни диапазона дат) — задание и так создаётся как самостоятельная единица (по модели из BOM либо вручную), что уже ближе к «один наряд-заказ = одно задание», чем к исходной недельной идее из ТЗ. Открытый пункт — не переделка модели данных, а два конкретных действия:

- [x] **Загрузка наряд-заказа как способ создания задания** — форма создания задания (12.4) получила третий способ, «Загрузить наряд-заказ», рядом с «По модели (BOM)»/«Вручную»: `.xls`-файл разбирается в строки (название детали, ширина/длина/кол-во), пользователь выбирает номенклатуру плёнки (файл её не содержит — цвет там только про дерево) и участок, дальше — обычное создание через уже существующий `POST /production-tasks/manual`. Два вида файла поддержаны одним и тем же загрузчиком (пробует по очереди): «Перечень деталей столярных изделий» (раздел «РАСКЛАДКА» — детали полотна: стоевая/поперечная/филёнка, явные колонки ширина/длина/кол-во) и погонажный (добор/наличник/короб — колонка «Кол-во ПЛАН», размеры зашиты в текст названия, "10х100х2070"). Парсер (`services/naryad_import.py`) ищет колонки по тексту заголовка, а не по фиксированному номеру — печатные формы этой ERP используют неодинаковую раскладку между файлами.
  - Технический блокер по первому образцу (`Наряд-заказ царга.xls`) не снят: файл — нестандартный `.xls` (не байт-в-байт правильный BIFF8), `xlrd`/SheetJS теряют синхронизацию с записями; Office File Validation блокирует и прямое открытие через Excel. Оба поддержанных вида — из **других** образцов (`ПечатнаяФорма_ПереченьДеталейСтолярныхИзделий[_ДоборныйПогонаж]_*.xls`, экспортированы из системы-источника напрямую, без промежуточного пересохранения) — если реальные наряд-заказы в работе будут только в первом (проблемном) формате, парсер нужно будет проверить/доработать под него отдельно, когда появится читаемый образец.
- [x] **Ширина/длина из наряда — это размеры детали (дерево), не плёнки** — первая версия загрузчика по ошибке копировала ширину/длину детали из файла прямо в `width_mm`/`length_m` строки задания, как если бы это уже был размер плёнки. Исправлено: `width_mm`/`length_m` остаются собственными размерами детали (так и задумано — совпадает с тем, что реально хранится в БД и для строк, введённых вручную), а ширина плёнки на укутку теперь считается через `calc_default_strip_width` по верифицированным константам из формул проекта `C:\Users\User\Downloads\Calc` (`interior_material_cost.py`): стоевая=292мм, поперечная=285мм, филёнка=356/474мм по ширине заготовки (163/220мм, с приблизительным запасным множителем ×2.17 для непроверенных ширин), наличник=120мм, добор=ширина+17мм. Короб — исключение: ширина полосы зависит от ДВУХ чисел профиля (ширина+глубина), которые есть только в тексте названия при разборе погонажного наряда — считается прямо там (`_korob_strip_width_mm`, таблица `KOROB_WRAP_WIDTHS_MM`) и идёт вместе со строкой, в обход `calc_default_strip_width`.
- [x] **Убрать терминологию/UI-остатки «недельного плана»** — переименовано в `Issue.tsx` («Строк в заданиях недели» → «Строк не распределено на сегодня», «Задания участка — на неделю» → «Не распределено на сегодня»), в `ProductionTasks.tsx` (вкладка «Все задания (Неделя)» → «Все задания»), в `OnboardingCard.tsx` (подсказка про «список на неделю» → «список заданий»). «Динамика по неделям» в `Defects.tsx`/`reports.py` не трогали — это реальные времянные бакеты отчёта, а не намёк на недельный ритм планирования.

## 15. Общий погонаж на партию — видимость и подбор донора по метражу, не по одной детали

Раньше и «Задания», и «Выдача участку» знали только расход на ОДНУ деталь (`line.length_m`) — ни то, ни другое место не показывало и не учитывало суммарный метраж на всю партию/строку.

- [x] **Видимость общего метража** — в «Заданиях» новая колонка «Погонаж на строку, м» (`quantity_pieces × length_m`) плюс сводка по плёнке над таблицей строк (итого на задание + сколько ещё выдать, группировка на случай, если строки всё же на разной номенклатуре). В «Выдаче участку» строка очереди на бригаду/день показывает не только «N шт», но и метраж рядом (`N шт (X м)`), группа из нескольких заданий на одну плёнку — итоговый метраж по всей группе.
- [x] **Подбор донора — по общему метражу партии, не по одной детали** — `POST /units/issue` и подбор донора реально уже фильтровали по `length_m >= payload.length_m`, но фронтенд передавал длину ОДНОЙ детали (`line.length_m`) вместо метража всей партии — отсюда и жалоба «выдали 4 отдельных штрипса, а хватило бы одного»: система искала (и находила) донора, которого достаточно на одну деталь, а не на все сразу. Один и тот же исправленный расчёт (`neededLengthM`, `frontend/src/pages/mobile/Issue.tsx`) теперь используется и для показа, и для запроса к бэкенду. Живая проверка (QA, до/после): запрос на длину одной детали брал короткого донора (2.5м), запрос на весь метраж партии (4×2.07=8.28м) — того же по возрасту, но длинного (10м).
- [x] **Число бригад/линий параллельно = число отдельных штрипсов — без отдельной логики** — оказалось, это уже устроено правильно на уровне данных: «сегодня»-строка очереди — это конкретная запись `ProductionTaskLineAssignment` (бригада + линия + день), и если по одной строке задания сегодня работают 3 бригады параллельно, это уже 3 РАЗНЫЕ строки очереди (`assignmentRows` строится через `flatMap` по всем assignment-записям, не агрегирует их) — каждая честно запросит донора на СВОЙ метраж. Если бригада одна — по строке задания одна assignment-запись, один запрос на весь метраж партии сразу. Никакого счётчика "число линий" заводить не пришлось.
