# UI-система БДК: правила унификации интерфейса

## Назначение

Единые правила для экранов React + Ant Design на ПК, планшетах и телефонах. Пользователь должен узнавать одинаковые таблицы, фильтры, карточки, статусы и действия во всех разделах. Содержимое и доступные операции определяются ролью и бизнес-процессом.

## Что обнаружено в аудите

- Основные навигационные хабы уже выделены: «Заказы», «Производство», «Плёнка», «Склад», «Закупки», «Аналитика» и настройки. Навигацию фильтруют права пользователя.
- Цветовая палитра и Ant Design theme уже заданы в `src/theme.ts`, но экраны используют разные плотности таблиц, ручные цвета, карточки и самописные HTML-таблицы.
- В проекте есть общий `ResponsiveTable`, но только часть списков им пользуется; многие экраны рендерят Ant Design `Table` напрямую.
- У `ResponsiveTable` мобильные карточки включены по умолчанию только на ширине `sm`. Поэтому планшеты часто продолжают получать широкие таблицы.
- Исторические предложения Antigravity включают сокращение вкладок, ролевые рабочие хабы, планшетные терминалы и удаление горизонтальной прокрутки как основного способа просмотра. Их следует применять с учётом фактически реализованной навигации и пользовательской иерархии, а не копировать механически.

## Информационная архитектура

Основной вход — рабочий хаб по роли. Один экран отвечает за один этап процесса; подэкраны объединяются в раздел, если относятся к тому же объекту и рабочей задаче. Вкладки второго и третьего уровня не должны дублировать верхнее меню.

Главная иерархия производства всегда сохраняется:

```text
Заказ клиента / счёт 1С / сделка Bitrix
└── Заказ на производство
    └── Задания участков
        └── Строки задания / детали
```

Складские и материальные операции привязываются к корректному уровню. Например, потребность в ПФ группируется по деталям или заданиям, но действия перемещения и выпуска показывают конкретное задание участка-получателя. Контекстные ссылки ведут вверх и вниз по иерархии, не смешивая сущности.

### Сценарии ролей

- **Менеджер продаж:** заказ клиента → состав/срок → передача в производство → готовность/отгрузка.
- **Начальник цеха / диспетчер:** заказ на производство → загрузка и потребность → задания участков → контроль выпуска.
- **Мастер участка:** задания своего участка → строка/деталь → отчёт, брак, материал и сверка у рабочего места.
- **Начальник склада плёнки / кладовщик:** приёмка → единица/рулон → остаток и адрес → выдача/перемещение → сверка.
- **Снабжение:** потребность/дефицит → поставщик и цена → заказ поставщику → приход.
- **Руководитель:** сводные показатели и отклонения с переходом к первичному заказу или заданию.

Права на данные и действия остаются permission-based. Планшетный режим не добавляет пользователю полномочий и не меняет порядок операций.

## Визуальные основы

Текущая палитра остаётся фирменной: тёмно-синий для каркаса и текста, оранжевый для главного действия, зелёный для подтверждённого результата, красный для дефицита/ошибки. Цвет всегда дополняется подписью или значком.

### Токены

| Роль токена | Значение |
|---|---|
| Текст и шапка | `#2C2E3A` |
| Вторичный текст | `#6B6B68` |
| Основное действие | `#C97A2B` |
| Успех | `#1D9E75` |
| Ошибка | `#C0392B` |
| Фон страницы | `#F1F1EE` |
| Поверхность | `#FFFFFF` |
| Граница | `#DEDEDA` |
| Радиус карточки | 12 px |
| Радиус контрола | 8 px |
| Сетка отступов | 4, 8, 12, 16, 24, 32 px |
| Сенсорная цель | не меньше 44×44 px |

`theme.ts` задаёт токены Ant Design; `index.css` применяет их к компонентам, которые Ant Design не позволяет выровнять одним theme token. Новые локальные HEX-цвета и произвольные радиусы в рабочих экранах не вводятся без системной причины.

## Шаблон рабочего экрана

1. **Заголовок:** одно название раздела, короткое объяснение при необходимости, справа — одно главное действие.
2. **Навигация уровня раздела:** одна полоса вкладок, если действительно есть несколько устойчивых режимов.
3. **Фильтры:** одна компактная зона над данными; частые фильтры — чипы, дополнительные — сворачиваемые.
4. **Данные:** единый компонент таблицы или карточек с общими заголовком, плотностью, пагинацией, пустым состоянием и действиями.
5. **Детали и операции:** раскрытие строки, боковая панель или модальное действие; не отдельная случайная карточка под таблицей.

Не использовать одновременно несколько конкурирующих «главных» кнопок. Деструктивные операции визуально отделять и подтверждать.

## Правила таблиц и карточек

Все таблицы, включая прямые вызовы Ant Design `Table`, используют общий визуальный ритм: одинаковый шрифт и числовые колонки, фон и вес заголовка, высоту строк, границы и hover-состояние. Различаться могут только колонки и бизнес-данные.

- **ПК:** таблица для сравнения и сортировки большого набора данных; закреплять ключевой идентификатор и действия, когда список действительно широкий.
- **Планшет:** рабочий список по умолчанию становится карточками/адаптивными строками с одним уровнем данных. В карточке сначала показываются идентификатор/деталь, статус, ключевой остаток/срок и главное действие.
- **Плитка:** отдельный режим просмотра для сканирования и выбора однотипных объектов; сетка подстраивается под ширину, не меняя доступных операций.
- **Второстепенные поля:** раскрываются в «Подробнее», но не теряются и остаются доступны для экспорта/печати.
- **Горизонтальная прокрутка:** оставлять для матриц и сравнительных таблиц, где одновременная видимость колонок имеет рабочий смысл. Не использовать как стандартный способ читать обычный список.
- **Сортировка, фильтры, выбор строк, раскрытие и действия:** должны сохранять функциональность при переключении представления.
- **Сенсорное управление:** кнопки, поля, вкладки и переключатели не меньше 44 px; соседние действия имеют визуальный зазор.

Сейчас общий CSS выравнивает внешний вид Ant Design `Table`, а `ResponsiveTable` отвечает за доступные карточные представления. При миграции любого табличного экрана сохранять все фильтры, выбор строк, вложенные детали, экспорт, пагинацию и действия.

## План миграции

### Фаза 1 — основы (выполнена в текущей ветке)

- Общие цветовые/spacing/radius CSS variables и токены таблиц.
- Единый вид таблиц и карточек через Ant Design theme и глобальные правила.
- Сенсорные цели 44 px для coarse pointer.
- Планшетное правило обновлено в `PROJECT_CONTEXT.md`: карточки — базовый сценарий рабочего списка; горизонтальный скролл — только обоснованное исключение.

### Фаза 2 — основные рабочие поверхности

1. Потребность ПФ и дневной план мастера.
2. Хаб плёнки: выдача, перемещение, сверка и приёмка.
3. Складские остатки, выдача/приёмка ПФ и инвентаризация.
4. Заказы и диспетчерское производство.

Для каждой поверхности определить первичное действие роли, видимые поля и drill-down до исходного заказа/задания.

### Фаза 3 — остальные экраны

- Перевести самостоятельные таблицы на общий адаптивный компонент или общий стиль.
- Удалить самописные таблицы и локальные варианты, если они не несут необходимого специального поведения.
- Упорядочить дублирующие маршруты только после проверки сценариев всех затронутых ролей и сохранения обратных ссылок.

## Проверка изменений

Проверять минимум на 768, 1024 и 1440 px, отдельно в портретной и альбомной ориентации планшета. Для ключевых ролевых сценариев проверять доступность первого действия, читабельность статуса и количества, переход по иерархии и отсутствие случайной прокрутки страницы по горизонтали. Сборка TypeScript/Vite подтверждает техническую целостность, но не заменяет просмотр на реальном планшете.

## Владение

`src/theme.ts`, `src/index.css`, `src/components/ResponsiveTable.tsx` и этот документ — основа системы. Новые варианты сначала добавляются сюда и в общий компонент; локальные варианты разрешены только для особого сценария данных и должны иметь обоснование.
