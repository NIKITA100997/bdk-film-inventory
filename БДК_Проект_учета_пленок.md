# Проект: учёт плёнки на производстве БДК

## 1. Цель и рамки

Организовать прослеживаемый учёт рулонов и отрезков плёнки — от приёмки (УПД, поддон, 9 рулонов) и недельного планирования цеха до выдачи на конкретный производственный участок и списания, с разделением мест и правил хранения для:
- **целых рулонов** (как пришли от поставщика),
- **штрипсов** (остатков ширины после продольной резки),
- **остатков длины** (после раскроя — физически возможен только на участке цельнолистовых дверей),
- **свободных остатков** (доступны для повторного использования/погонажа).

Ключевое требование: каждый физический рулон/штрипс/отрезок — отдельная единица учёта с привязкой к партии (УПД), а не агрегированные квадратные метры, как сейчас в 1С ("Аляска — 2000 м²"). Поверх этого — недельное планирование цеха, посуточная выдача трём производственным участкам, план/факт расхода и рекомендательная логика по использованию неходовых остатков ширины вместо раскроя новых рулонов. Отдельное внимание — единицам измерения: м² и метры погонные нужны на разных уровнях и не взаимозаменяемы (см. 2.2).

## 2. Модель данных

### 2.1. Сущность "Единица плёнки" (Roll/Piece)

Каждый физический объект — рулон, штрипс или отрезок — одна запись с уникальным ID (штрихкод/QR на этикетке).

| Поле | Описание |
|---|---|
| `id` | Уникальный номер единицы (печатается на этикетке) |
| `parent_id` | Ссылка на "родителя" (пусто для рулона от поставщика или если единица продолжает жить под тем же ID при разделении — см. 2.4) |
| `upd_number` | Номер УПД поступления |
| `pallet_number` | Номер поддона в рамках УПД |
| `material` | Материал плёнки |
| `color` | Цвет |
| `thickness` | Толщина |
| `manufacturer` | Производитель |
| `width_mm` | Текущая ширина |
| `length_m` | Текущая длина в метрах погонных (м.пог) — актуальна всегда, обновляется при каждом разделении и возврате |
| `area_m2` | Вычисляемое поле, не хранится: `width_mm × length_m ÷ 1000`. Используется только для агрегированной отчётности (карточка материала, план/факт) — см. 2.2 |
| `status` | `Принят` / `На_хранении` / `Выдан_участку` / `Списан` |
| `area` | Участок, у которого сейчас находится единица (пусто, если на складе): `Окутка_царговых` / `Щитовые_двери` / `Цельнолистовые_двери` |
| `zone` / `cell` | Текущий адрес ячейки (только пока единица физически на складе — рулонный/штрипсовый стеллаж, или стеллаж Б на цельнолистовых) |
| `order_id` | Мягкая привязка к производственному заказу (опционально) |
| `created_at`, `updated_at` | Метки времени |

Ширина и длина не печатаются на этикетке (см. 4.1) — актуальные значения всегда смотрим в приложении по QR/ID.

### 2.2. Единицы измерения: м² и метры погонные

Смешивать эти две единицы — источник постоянной путаницы, поэтому в системе они разведены по разным уровням работы:

**м² (площадь)** — полезны только там, где материал ещё **не привязан к конкретной ширине**. Целый рулон можно раскроить на любую ширину, поэтому м² дают сопоставимую единицу для вопроса "хватит ли материала в принципе на неделю" — независимо от того, на какие именно ширины его в итоге разрежут. Используется:
- в недельном плане и заявке на плёнку (2.7) — точные ширины на этом этапе обычно ещё не известны;
- в верхней сводной цифре карточки материала (2.6) — "сколько всего материала этой позиции у нас есть", суммарно по всем ширинам;
- при сравнении план/факт (2.8) на уровне позиции плана.

**Метры погонные (м.пог, далее просто "метры" применительно к конкретной единице)** — как только мы имеем дело с конкретным физическим рулоном или штрипсом **фиксированной ширины**, м² перестают быть операционно полезны: 50 м² при ширине 400 мм не помогут, если нужно 20 погонных метров при ширине 1000 мм. Важна именно длина при данной ширине. Используется:
- везде на складе и участках — выдача, разделение, раскрой, поиск остатка, проверка "хватит ли этого штрипса под запрос";
- в разбивке по ширине внутри карточки материала;
- в ABC-анализе ширин (2.9) — расход ранжируется по метрам при каждой конкретной ширине, м² там смысла не несут, так как ширина уже зафиксирована самой классификацией.

**Принцип для интерфейса:** приложение не даёт выбор единицы вручную — использует м² там, где ширина ещё не конкретизирована (план), и метры там, где работа идёт с конкретной физической единицей (склад, участки). Так исключается ситуация, когда сотрудник случайно сравнивает разнородные величины.

### 2.3. Правило маркировки при разделении

Материал, цвет, толщина и производитель не меняются при разделении рулона — меняются только ширина и/или длина. Раз эти изменяющиеся параметры не печатаются на этикетке, а живут только в базе, разделение рулона не обязано порождать новую бирку для обеих результирующих частей.

**Правило:**
- Одна из двух частей считается **продолжением** исходной единицы — сохраняет тот же `id` и ту же физическую бирку, в приложении обновляются только `width_mm`/`length_m`. Как правило, это часть, что едет дальше по технологическому пути.
- Другая часть — та, что физически **отделяется** (уходит в другое место) — получает новый `id`, `parent_id` = id исходной единицы, и новую бирку, если ей предстоит где-то полежать.
- Если отделяемая часть сразу и полностью уходит в производство — новая бирка не печатается вообще, достаточно события в журнале.

Итог: при типичной продольной резке печатается не более одной новой бирки, а не двух.

### 2.4. Два типа операций разделения

**Продольная резка (по ширине)** — всегда на складе плёнки. Длина у обеих результирующих частей одинаковая, меняется только ширина:
- Часть нужной ширины — как правило, "продолжение" (тот же ID), едет на выдачу участку.
- Штрипс-остаток — как правило, новая единица, на штрипсовый стеллаж.

**Раскрой (по длине)** — физически возможен только там, где деталь требует дискретного куска точного размера:
- На складе — если режется новый рулон под цельнолистовые двери (совмещённая операция ширина+длина).
- На участке цельнолистовых дверей — на их собственном раскройном месте (стеллаж Б).
- Окутка царговых составляющих и щитовые двери раскрой по длине не используют — материал подаётся в процесс непрерывно с рулона.

### 2.5. Партионность

`upd_number` + `pallet_number` наследуются к каждой новой единице (новый `id`) при разделении. Если часть продолжает жить под тем же ID, партия не меняется.

### 2.6. Карточка материала (агрегированное представление)

Отдельная сущность физически не хранится — представление, собирающее все единицы с одинаковыми `материал + цвет + толщина + производитель` в одну карточку.

Состав карточки:
- **Общий остаток, м²** — сумма `area_m2` по всем физическим единицам этой группы, независимо от ширины. Отвечает на вопрос "сколько всего материала этой позиции у нас есть".
- **Таблица по ширинам** — ключевой блок, не просто 2–3 сводные цифры, а полный список: **каждая ширина, которая физически есть в наличии** (а не только "ходовые"), с колонками "сколько метров" и "где сейчас находится" (конкретный адрес на складе — `Р-3-07`/`Ш-2-04-06` — либо участок, если выдано: Окутка царговых / Щитовые двери / Цельнолистовые двери). Отвечает не только на вопрос "хватит ли метров при этой ширине", но и "где физически искать" — без похода на склад и без звонка кладовщику.
- **Разбивка по статусам** — на хранении / выдано участкам (с разбивкой по трём участкам).
- **Список физических единиц** — ID, текущая ширина×длина, адрес ячейки/участок, статус (та же информация, что и в таблице по ширинам, но на уровне конкретных ID, а не агрегата по ширине — для случаев, когда на одной ширине несколько разных единиц в разных местах).
- **План/факт** — плановая площадь на неделю (м²) против фактического расхода (см. 2.8).
- **Журнал движений** — хронологическая лента событий.

**Журнал событий (`MaterialEvent`) — источник данных для карточки:**

| Поле | Описание |
|---|---|
| `event_id` | Уникальный ID события |
| `unit_id` | К какой единице относится |
| `material_key` | Материал+цвет+толщина+производитель — для группировки в карточке |
| `event_type` | `Приход` / `Продольная_резка` / `Раскрой` / `Выдача_участку` / `Возврат` / `Списание` / `Привязка_к_заказу` / `Снятие_привязки` |
| `area` | Участок, если событие с ним связано |
| `timestamp` | Дата и время |
| `user` | Кто выполнил действие |
| `width_mm` | Ширина единицы на момент события — нужна, чтобы потом пересчитать метры в м² при агрегации |
| `from_length`, `to_length` | Изменение длины (метры погонные) |
| `from_cell`, `to_cell` | Изменение адреса ячейки |
| `order_id` | Если событие связано с заказом |
| `quantity_delta_m` | Изменение длины в метрах погонных (для приходов положительное, для списаний отрицательное) |

Журнал заполняется автоматически при каждом действии в приложении. `width_mm` в каждой записи позволяет в любой момент агрегировать историю как в метрах (по конкретной ширине), так и в м² (просуммировав `width_mm × quantity_delta_m ÷ 1000` по нужному срезу) — не требуя пересчёта задним числом.

### 2.7. Недельное планирование

| Сущность | Поля | Назначение |
|---|---|---|
| `WeeklyPlan` | id, неделя (с–по), создал (начальник цеха), статус | План работ цеха на неделю |
| `FilmRequestLine` | id, weekly_plan_id, материал, цвет, толщина, плановая площадь (**м²**) | Позиция заявки на плёнку — в м², так как точные ширины на этом этапе обычно ещё не известны |

Заявка служит резервом объёма, а не жёстким списком ширин: отвечает на вопрос "хватит ли материала в принципе на неделю". Если не хватает — это сигнал для снабженца/закупщика заказать недостающее у поставщика (это единственная его функция в системе — см. роли в разделе 6).

### 2.8. План/факт расхода по участкам

- **План** — из `FilmRequestLine`: плановая площадь на неделю, **м²**.
- **Факт** — из журнала `MaterialEvent`: сумма `width_mm × quantity_delta_m ÷ 1000` по событиям `Выдача_участку`/`Списание` за тот же период → тоже в **м²**, чтобы быть сопоставимым с планом.

Отчёт "План/факт" (десктоп, см. 5.4) показывает по каждой позиции: план (м²) | факт на сегодня (м²) | % выполнения | прогноз на конец недели. Дополнительно — по клику можно провалиться в разбивку факта по конкретным ширинам в метрах (для операционного понимания, что именно расходовалось, а не только агрегат).

### 2.9. ABC-анализ ширин и рекомендация "донор-штрипс"

**Проблема:** штрипсы нестандартной ширины, не подходящие ни под одну ходовую деталь, копятся на складе мёртвым грузом, а под новые запросы режутся новые целые рулоны вместо использования уже существующего остатка.

**Классификация ширин (ABC по фактическому расходу в метрах):**
- За период (например, 3 месяца) считается фактический расход **в метрах погонных** по каждой конкретной ширине — из `MaterialEvent` (`event_type = Выдача_участку`), отдельно на каждую комбинацию материал+цвет+толщина. М² здесь не нужны — ширина уже зафиксирована самой классификацией, площадь ничего не добавляет.
- Топ ~80% расхода — класс А (ходовые), следующие ~15% — класс B, остаток ~5% — класс C (неходовые).
- Пересчитывается автоматически, например раз в месяц.

**Алгоритм подбора при выдаче (запрос на ширину W, длину L метров):**
1. Точное совпадение — есть штрипс шириной ровно W с длиной ≥ L → выдать (тот же ID, просто меняется `area`/`status`).
2. Точного совпадения нет — поиск штрипсов шириной больше W, классифицированных как B/C, с минимальным отходом (`ширина_штрипса − W` минимальна среди кандидатов).
   - Найден донор → приложение предлагает: *"Есть штрипс №…, ширина 220 мм, класс C. Рекомендуем отрезать 212 мм, отход 8 мм."* Оператор подтверждает или выбирает "резать новый рулон".
3. Подходящего донора нет — резать новый целый рулон.

**Минимальная полезная ширина** — куски уже некоторого порога (например, 30–50 мм — нужно уточнить с производством) автоматически считаются отходом.

## 3. Статусная модель (жизненный цикл)

```
1. Принят        — на приёмке, привязан к УПД/поддону
2. На хранении     — целый рулон (зона А) или штрипс (зона С), area = пусто
3. Выдан участку   — area = Окутка_царговых / Щитовые_двери / Цельнолистовые_двери
4. Возврат         — в любой момент, когда участок решает, что остаток
                      больше не нужен (внутренний регламент участка)
                      → снова "На хранении", зона С, area очищается
5. Списан          — использован в производстве полностью, выбывает из учёта
```

Разделение (продольная резка/раскрой) может происходить из статуса "На хранении" или "Выдан участку" (раскрой на месте у цельнолистовых) — по правилам 2.3: одна результирующая часть продолжает жить под тем же ID с обновлённой длиной, другая — новая единица либо сразу списывается.

**Мягкая привязка к заказу:** пока единица числится с `order_id`, участок по умолчанию использует именно её при повторном раскрое по этому заказу — подсказка в интерфейсе, а не жёсткое ограничение.

## 4. Инфраструктура хранения: склад плёнки и стеллаж на цельнолистовых

Хранение — не один стеллаж, а **склад плёнки**, физически состоящий примерно из 10 стеллажей на сегодня, с ростом их числа дальше. Все — вертикальные механизированные, циклические (кнопки вверх/вниз), без программной адресации, открытого типа. Стеллажи на складе делятся на **два типа по тому, что на них хранится**, а не по статусу единицы:

| Тип стеллажа | Что хранится | Правило заполнения | Обозначение |
|---|---|---|---|
| **Рулонный** | Целые (непочатые) рулоны | Одна полка = один рулон (рулоны крупные, штучное хранение) | Р-1, Р-2, Р-3 … |
| **Штрипсовый** | Штрипсы — любые, независимо от статуса: свежий остаток после продольной резки, буфер, свободный остаток | На одной полке — несколько штрипсов (до ~10, зависит от ширины: чем уже штрипс, тем больше их помещается) | Ш-1, Ш-2, Ш-3 … |

Статус единицы (на хранении / выдан участку / в буфере заказа) — это состояние в приложении, а не физическая зона: штрипс остаётся на том же штрипсовом стеллаже независимо от того, свободен он или числится за конкретным заказом. Разделение по типу стеллажа отражает физическую реальность — рулон и штрипс требуют разных полок по своим габаритам, а не разного логического статуса.

Отдельно, на участке цельнолистовых дверей — **стеллаж Б**, того же (штрипсового) типа, физически отдельно расположен там же, где выполняется локальный раскрой.

**Окутка царговых составляющих и щитовые двери** формального места хранения не имеют — выданный рулон/штрипс находится у их рабочего места, адрес ячейки в приложении не ведётся.

**Правило ячейки:** на рулонном стеллаже отдельная ячейка внутри полки не нужна (полка = рулон). На штрипсовом стеллаже (включая Б) — ячейки внутри полки нумеруются, несколько штрипсов на полке хранятся по отдельным ячейкам либо, для совсем мелких, партией с общим списком ID.

## 4.1. Адресация ячеек и этикетка

### Формат адреса — разный для двух типов стеллажей

- **Рулонный стеллаж:** `[Стеллаж]-[Полка]`, например `Р-3-07` — стеллаж Р-3, полка 7. Ячейка не нужна, так как полка = один рулон.
- **Штрипсовый стеллаж (включая Б):** `[Стеллаж]-[Полка]-[Ячейка]`, например `Ш-2-04-06` — стеллаж Ш-2, полка 4, ячейка 6.

Каждый стеллаж на складе нумеруется независимо и получает свою литеру при вводе в эксплуатацию (Р-1, Р-2… для рулонных; Ш-1, Ш-2… для штрипсовых) — при добавлении новых стеллажей (склад растёт) просто добавляется следующий номер, ничего не переразмечается.

### Разметка (сделать один раз на каждый стеллаж, до запуска)

1. **Точка отсчёта** — нумерация полок снизу вверх, у пульта табличка-подсказка направления.
2. **Номера полок** — табличка на переднем крае каждой полки, шрифт от 40 мм.
3. **Ячейки внутри полки** (только для штрипсовых стеллажей и Б) — разделители с номерами слева направо; сколько ячеек на полку — зависит от того, штрипсы какой ширины на неё определены (макрозонирование).
4. **Карта-указатель у пульта** каждого стеллажа — какие материалы/цвета на каких полках.
5. **Справочник ячеек в приложении** — заводится один раз при вводе каждого стеллажа в систему; при добавлении нового стеллажа справочник просто расширяется.

### Макрозонирование

Полки распределяются по группам "материал + цвет" — как между стеллажами одного типа (какой рулонный/штрипсовый стеллаж отвечает за какую товарную группу), так и внутри полки. До готовности ABC-анализа — временно по алфавиту.

### Этикетка (физическое исполнение)

Печатается один раз при создании единицы (приёмка либо разделение — если часть отделяется и остаётся в системе, см. 2.3). Не перепечатывается при изменении ширины/длины.

Состав, сверху вниз:
1. **Цветная полоса-индикатор** — статус на момент печати (зелёная — целый рулон; синяя — штрипс/буфер; серая — свободный остаток).
2. **QR-код** — крупный, по центру.
3. **ID единицы** — крупным шрифтом под QR-кодом.
4. **Материал / Цвет / Толщина / Производитель** — крупным шрифтом (не меняются в течение всей жизни единицы).
5. Мелким шрифтом: № УПД, № паллеты, дата приёмки; для новых единиц при разделении — "Из рулона №[ID родителя]".

**Ширина, длина и площадь на этикетке не печатаются** — актуальные значения смотрим в приложении по QR/ID, в контекстно верной единице (метры на складе/участках, м² — на уровне отчётности).

## 5. Инструментарий и функциональность приложения

### 5.1. Вводные

- Принтеры этикеток уже есть.
- Сканирование — с личных/рабочих телефонов (камера) и с ТСД.
- До 20–30 одновременных пользователей.
- Закрытие заказа: основной путь — ручная кнопка в приложении, интеграция с 1С — опциональное усиление.

### 5.2. Архитектура (кратко)

Backend: FastAPI + PostgreSQL. Frontend: адаптивный веб — мобильная версия для цеха и ТСД, десктопная — для снабжения, склада, начальника цеха и логиста.

### 5.3. Мобильная версия — экраны

**Главный экран** — меню зависит от роли: Приёмка, Выдача участку, Разделить рулон, Раскрой, Возврат, Размещение в ячейку, Поиск остатка.

**Экран "Приёмка"** — без изменений.

**Экран "Разделить рулон" (продольная резка):**
1. Сканирование ID — приложение подтягивает текущие параметры, длина показывается в метрах (не в м²).
2. Ввод ширины отрезаемой части.
3. *"Останется: 1000 мм, тот же ID — бирка не меняется. Новый штрипс: 400 мм, 500 м — нужна бирка?"*
4. Печать бирки (если остаётся в системе) или списание без бирки (если сразу в производство).

**Экран "Выдача участку":**
1. Выбор участка.
2. Ввод нужной ширины и длины в метрах (не в м²) — именно столько нужно физически под задачу дня.
3. Подбор по алгоритму 2.9: точное совпадение → донор-штрипс → резать новый рулон.

**Экран "Раскрой"** (только цельнолистовые двери) — аналогично "Разделить рулон", но по длине.

**Экран "Возврат"** — сканирование ID, ввод фактической текущей длины в метрах, подтверждение.

**Экран "Поиск остатка"** — фильтр по минимальной длине задаётся в метрах при конкретной ширине, не в м².

### 5.4. Десктопная версия — экраны

**Раздел "Недельный план"** — ввод плана в **м²** по позициям материал/цвет/толщина.

**Раздел "План/факт"** — план (м²) | факт (м²) | % выполнения | прогноз, с провалом в разбивку по ширинам в метрах.

**Дашборд остатков** — таблица единиц, длина указывается в метрах (это конкретные физические объекты фиксированной ширины).

**Карточка материала** — сверху общий остаток в м², ниже полная таблица по всем ширинам в наличии с текущим местоположением каждой (склад: адрес стеллажа, или участок: где выдано) — см. 2.6.

**Раздел "Рекомендации по резке"** — штрипсы класса C, длина в метрах.

**Раздел "Отчёты"** — остатки по материалу/цвету/толщине (м²) и по конкретной ширине (метры), движение за период.

**Раздел "Настройки"** — справочник ячеек, макрозонирование, порог минимальной полезной ширины, период пересчёта ABC-классов.

**Раздел "Заказы"** — список заказов с привязанными остатками, кнопка "Закрыть заказ".

## 6. Физический процесс по шагам (кто, что, как)

### 6.1. Недельное планирование

1. Начальник цеха формирует план работ на неделю.
2. В приложении формируется заявка на плёнку — материал/цвет/толщина + плановая площадь в **м²**.
3. Система сравнивает заявку с текущим остатком (тоже в м²) — при нехватке формируется сигнал для снабженца/закупщика (это и есть повод для его единственного действия в системе — заказать недостающее у поставщика).

### 6.2. Приёмка

1. Паллета (9 рулонов) + УПД. Оператор склада сверяет количество.
2. Сканирует/вводит УПД и паллету — создаются 9 записей.
3. Печатается и крепится бирка на каждый рулон.
4. Рулоны размещаются на подходящем рулонном стеллаже по макрозоне.

### 6.3. Выдача участку

1. Начальник участка сообщает задачу дня — материал, цвет, толщина, точная ширина и нужная длина **в метрах**.
2. Оператор склада ищет соответствие: точный штрипс → выдаёт; донор класса B/C → предлагает отрезать; ничего подходящего → режет новый рулон.
3. Статус → "Выдан участку".

### 6.4. Использование на участке

- **Окутка царговых, щитовые двери:** материал расходуется непрерывно через процесс — раскрой по длине не требуется.
- **Цельнолистовые двери:** раскрой на месте под конкретные панели, остаток остаётся на стеллаже Б.

### 6.5. Возврат

1. Когда участок решает, что остаток не нужен — сканирует ID, подтверждает возврат, фактическая длина в метрах фиксируется.
2. Статус → "На хранении", зона С.

### 6.6. Закрытие заказа

1. Готовое изделие отгружается со склада.
2. Логист/кладовщик нажимает кнопку "Закрыть заказ" — основной путь, работает всегда.
3. Опционально — событие в 1С вызывает ту же операцию автоматически.

### 6.7. Выдача под погонаж (свободные остатки)

1. Запрос: нужен кусок такого-то цвета/толщины, от N метров при определённой ширине.
2. Кладовщик фильтрует штрипсовые стеллажи по метрам при нужной ширине, выбирает оптимальный.
3. Списывает (или создаёт потомка, если кусок больше нужного).

### Сводная таблица по ролям

| Роль | Ключевые действия |
|---|---|
| Начальник цеха | Формирует недельный план (м²), следит за план/факт |
| Начальники участков (все три) | Суточный запрос ширины/длины в метрах, возврат остатка когда не нужен |
| Начальник участка "Цельнолистовые двери" | Дополнительно: локальный раскрой на своём стеллаже Б |
| Оператор склада плёнки | Приёмка партии, печать этикеток, продольная резка, совмещённая резка в размер для цельнолистовых, решения штрипс/донор/новый рулон |
| Кладовщик | Размещение по макрозонам, приём возвратов, выдача под погонаж |
| Снабженец/закупщик | Только закупка у поставщика — и только когда система сигнализирует нехватку (недельная заявка против остатка). В повседневных складских операциях (приёмка, выдача, резка) не участвует |
| Логист/руководитель | Закрытие заказов, отчёты, карточка материала, план/факт |

## 7. Статус вопросов

Закрыто вашими ответами (в этой и предыдущих итерациях):
- Печать этикеток, устройства, нагрузка — есть, без ограничений.
- Стеллаж Б — только на участке цельнолистовых дверей.
- Раскрой по длине — только там, где физически есть раскройное место.
- Возврат остатка — единый процесс, момент определяется регламентом участка.
- Этикетка без ширины/длины — актуальные значения через QR/приложение.
- Единицы измерения — м² на уровне плана/отчётности, метры погонные — на уровне конкретной физической единицы.

**Осталось открытым:**
- ABC-анализ по цветам/толщинам — будет готов после утверждения плана.
- Минимальная полезная ширина остатка (порог отхода) — нужно значение в мм от производства.
- Нужна ли окутке царговых и щитовым дверям формальная временная полка/тележка у рабочего места — пока предполагается, что рулон лежит у машины без адресации.
