## 1. Общие сведения и назначение системы

**Проект:** Комплексная система производственного, складского и оперативного учёта для **Белорусского дверного комбината (БДК)**.
- **Главная цель:** Сквозной партионный учёт материалов (рулоны плёнки, штрипсы, кромка, МДФ, брус), полуфабрикатов (стоевые, поперечные, филёнки, щиты, заготовки) и готовой продукции; планирование загрузки участков, диспетчеризация цеха, формирование сменных нарядов с QR-кодами, списание сырья по FIFO и контроль брака/перерасхода.

### Производственная география и специфика:
- **Площадка «Северный»:** Основной склад сырья и плёнки, форматно-раскроечные станки, нарезка штрипсов, вакуумные прессы, окутка погонажа и царговых элементов.
- **Площадка «Фабрика»:** Участок щитовых дверей, доборный погонаж, сборка каркасов, прессы горячей склейки, фрезеровка и шлифовка МДФ, кромкооблицовка, упаковка.
- **Особенность перемещений:** Сырьё и полуфабрикаты нарезаются/готовятся на Северном и партиями перемещаются на Фабрику. На Фабрике нет отдельного начальника склада, поэтому учёт должен быть максимально быстрым и дружелюбным к мастерам участков (планшеты, сканирование QR).

### Технологический стек:
- **Backend:** Python 3.12+ / FastAPI / SQLAlchemy / Alembic / PostgreSQL / Uvicorn.
- **Frontend:** React 19 / TypeScript / Vite / Ant Design (antd v6) / TanStack Query (v5).
- **Печать и сканирование:** Векторные SVG QR-коды, библиотека `html5-qrcode` для камер планшетов/смартфонов, термопечать этикеток (Codex G500 / PDF) и листы формата А4 landscape для сменных нарядов.
- **Интеграции:** Выгрузки счетов и спецификаций из 1С:Предприятие, вебхуки и лиды из Bitrix24.

## 3. Градация сущностей системы (Устранение путаницы)

В системе выстроена четкая 4-уровневая иерархия:

```
[Заказ клиента / Счёт 1C / Bitrix24] 
                 │
                 ▼
     [Заказ на производство (ProductionOrder)]
                 │
                 ▼
       [Задание на участок (ProductionTask)]  ──► QR-код "TASK:<id>"
                 │
                 ▼
         [Строка задания (ProductionTaskLine)]
```

1. **Заказ клиента (CustomerOrder / Deal):**
   - Коммерческий документ от отдела продаж.
   - Содержит номер счёта 1С, дату отгрузки покупателю, контрагента, список готовой продукции (например, 20 дверей «Модель 01», цвет «Дуб сонома»).
   - Менеджер по продажам работает только на этом уровне, не вмешиваясь в технологические этапы цеха.

2. **Заказ на производство (ProductionOrder):**
   - Запуск партии в производство (формируется диспетчером/начальником производства).
   - Объединяет один или несколько заказов клиентов либо запускается «на склад».
   - Имеет статусы: `draft` (черновик), `released` (запущен в работу), `completed` (завершен), `closed` (закрыт).
   - При запуске формирует спецификацию потребности сырья, резервирует плёнку и генерирует технологическую цепочку заданий по участкам.

3. **Задание на участок / цеховое задание (ProductionTask):**
   - Конкретная работа для одного участка/станка (например, *«Фрезеровка МДФ Фабрика»*, *«Окутка Северный»*, *«Сборка каркаса»*, *«Пресс склейки»*).
   - Именно на этом уровне формируется **сменный наряд-задание** и генерируется QR-код вида `TASK:<id>`.
   - Имеет плановые даты начала/окончания, статус (`pending`, `in_progress`, `completed`), привязку к мастеру и станку.

4. **Строка задания (ProductionTaskLine):**
   - Подетальный технологический элемент внутри наряда (наименование заготовки, размеры $H \times W \times T$, цвет, программа ЧПУ, количество плановое и сделанное годное/брак).

## 4. Хроника и контекст текущего диалога

### 4.1. Умное списание штрипсов на доборном погонаже (Пул FIFO)
- **Контекст проблемы:** На Фабрике изготавливается доборный погонаж. Ранее требовалось перемещать конкретные рулоны/штрипсы и мастеру отчитываться по каждому номеру индивидуально. Из-за отсутствия постоянного кладовщика на площадке это вызывало простои и задержки отчётов.
- **Принятое решение:**
  1. На Северном нарезаются штрипсы и отправляются перемещением на Фабрику.
  2. Для участка Фабрики важен только **цвет и точная ширина** (допуски нарезаются на Северном сразу в размер).
  3. Мастер берёт любой физический штрипс с поддона, а система списывает метраж по алгоритму **FIFO из пула штрипсов** соответствующего цвета и ширины.
  4. Если физически штрипса не хватило, разрешено проведение отчёта с фиксацией **минусового остатка (овердрафта)** по заданию с последующей подпиткой или локальной экспресс-инвентаризацией.

### 4.6. Безадресное списание штрипсов (FIFO-пул участка) и контроль овердрафта
- **Бизнес-логика:**
  - На участках без обязательного ручного сканирования рулонов (Фабрика / доборный погонаж) штрипсы списываются автоматически по алгоритму **FIFO** из пула доступных на участке штрипсов.
  - Поиск штрипсов в пуле участка (`get_area_matching_strips`) сопоставляет `material_id`, `color_id` и целевую ширину `target_width_mm`.
  - **Поддержка групп аналогов ширин (`WidthAnalogGroup`):** интеграция с `equivalent_widths(db, target_width_mm)` позволяет автоматически подбирать взаимозаменяемые штрипсы (например, 220 мм и 221 мм) из одной группы аналогов без ручных правок.
  - При недостатке точной толщины реализован fallback на совпадение по материалу, цвету и ширине.
  - **Овердрафт (дефицит):** если физически в пуле участка метров не хватает, отчёт мастера не блокируется ошибкой 422 — доступный остаток списывается в 0, а недостающий метраж фиксируется как дефицит (`film_deficit_m` / note `Дефицит плёнки: X м...`).
- **Визуальные индикаторы на экранах:**
  1. **Карточка задания (`TaskCardDrawer.tsx`):**
     - В столбце «Рулон / Штрипс» для участков без обязательного рулона выводятся бейджи:
       - Зелёный: `В пуле: {stock} м ({count} шт.) · FIFO`
       - Красный: `Дефицит: -{deficit} м` (при наличии овердрафта)
       - Серый: `Пул пуст (0 м)`
  2. **Дневной план мастера (`DailyPlanTab.tsx`):**
     - В столбце «Штрипс» отображается ширина, наличие в пуле участка `в пуле {stock} м` (зелёный тег) и овердрафт `дефицит -{deficit} м` (красный тег).
  3. **Быстрый отчёт мастера (`MasterQuickReportPanel.tsx`):**
     - При отсутствии требования рулона (`!requiresRoll`) добавляется колонка «Штрипс / Пул» с шириной, метражом в пуле и предупреждением об овердрафте. Под наименованием детали также подсвечивается `дефицит пула: -{deficit} м`.
  4. **Монитор производства (`AreasView.tsx` и `OrdersView.tsx`):**
     - В `AreasView` в колонке «Позиция» отображается красный бейдж `дефицит плёнки -{deficit} м`.
     - В `OrdersView` в ячейке `FilmCell` отображается предупреждение об овердрафте `дефицит -{deficit} м`.

### 4.7. Локальная экспресс-инвентаризация пула штрипсов на участке (Корректировка остатков)
- **Бизнес-логика:**
  - Мастер цеха или оператор станка прямо у рабочего места может сверить фактический метраж штрипса конкретной ширины/цвета в пуле участка.
  - Бэкенд-сервис: `adjust_strip_pool_stock` (`POST /api/production-tasks/strip-pool/adjust`):
    - Принимает: `area`, `material_id`, `color_id`, `thickness_id`, `target_width_mm`, `actual_meters`, `note`.
    - Рассчитывает дельту: `delta = actual_meters - current_meters`.
    - **Недостача (`delta < 0`):** списывает избыточные метры по FIFO с фиксацией события `EventType.INVENTARIZATSIYA_NEDOSTACHA`.
    - **Излишек (`delta > 0`):** создаёт единицу штрипса на участке с типом события `EventType.INVENTARIZATSIYA_IZLISHEK`.
    - Автоматически обнуляет зафиксированный ранее дефицит (`film_deficit_m = 0`) в активных строках заданий участка при приведении остатка в соответствие.
- **Интерфейс и UX:**
  - Модальное окно `StripPoolAdjustModal.tsx`:
    - Расчёт дельты в реальном времени, валидация, отображение текущего и нового метража.
    - Сенсорные кнопки быстрого добавления/сброса для планшета (`+10 м`, `+50 м`, `+100 м`, `= 0`).
    - Кнопка вызова «сверка» (иконка весов ⚖️) встроена в:
      - Карточку наряда (`TaskCardDrawer.tsx`) рядом с бейджем пула.
      - Дневной план мастера (`DailyPlanTab.tsx`) рядом с тегом наличия штрипса.
      - Быстрый отчёт мастера (`MasterQuickReportPanel.tsx`) в колонке «Штрипс / Пул».

### 4.9. Комплексная оптимизация производительности (устранение медленной загрузки на проде)
- **Причины тормозов на проде:**
  - Лавина параллельных запросов (до 25–30 запросов) при открытии главной страницы `ModularHome` (виджет «Сводка» / `Overview embedded` опрашивал 21 эндпоинт одновременно).
  - Голодание стандартного пула соединений SQLAlchemy (`pool_size=5, max_overflow=10` — лимит 15 соединений).
  - Проблема N+1 в сериализаторе `_task_out` (расчёт остатков рулонов делал по 2 SQL-запроса на каждый рулон).
  - Отсутствие индексов в PostgreSQL на таблицах `production_tasks`, `production_task_lines`, `production_task_line_reports`, `material_units` и `material_events`.
  - Утечка бандла: статический импорт `SearchBox` из `Overview.tsx` в `homeModules.tsx` ломал code-splitting и утягивал весь экран `Overview` в стартовый чанк.
  - Поведение TanStack Query (`staleTime: 0`, `refetchOnWindowFocus: true`), вызывавшее повторный шквал запросов при каждом переключении окон.
- **Внедрённые решения:**
  1. *Бэкенд батчинг (коммит a247022):*
     - Реализован `fetch_consumed_length_by_unit_since_issue` в `plan_fact.py` и `_preload_issued_unit_remaining` в `production.py` (1 пакетный SQL-запрос вместо 200).
     - Добавлен фильтр `active_only` в `/production-tasks`.
     - Создан легковесный специализированный эндпоинт `GET /film-issue/mobile-queue` со схемой `FilmIssueQueueTaskOut` для планшетов выдачи.
     - Батчинг маршрутов деталей и участков в `pf-demand`.
  2. *Пул БД и индексы (коммит e412d21):*
     - Пул SQLAlchemy расширен до `pool_size=20, max_overflow=20, pool_timeout=30`.
     - Создана миграция Alembic `b5e7d1a3c9f2` с 11 индексами:
       - `production_tasks (is_active)`, `(area, is_active)`, `(created_at)`.
       - `production_task_lines (task_id)`, `(task_id, is_closed)`.
       - `production_task_line_reports (task_line_id)`, `(reported_at)`, `(task_line_id, counts_toward_line)`.
       - `production_task_line_assignments (task_line_id)`, `(date)`.
       - `material_units (status)`, `(area, status)`, `(production_task_line_id)`.
       - `material_events (unit_id, event_type, timestamp)`.
  3. *Фронтенд и TanStack Query (коммит edab166):*
     - Установлены глобальные `staleTime: 30_000` и `refetchOnWindowFocus: false`.
     - Компонент `SearchBox` вынесен в отдельный модуль `components/SearchBox.tsx`, устранён `INEFFECTIVE_DYNAMIC_IMPORT`, `Overview` теперь собирается в отдельный ленивый чанк.
     - В `Overview.tsx` отключена фоновая загрузка 30-дневных тяжелых аналитических отчётов, когда компонент встроен в главную страницу (`embedded === true`).
