## Контекст

Проект перешёл в официальную эксплуатацию. Работа над ним разделена на
два трека: (1) доработки существующего учёта плёнки и (2) новые
направления — первое из них — **учёт п/ф**: заготовок (стоевая,
поперечная, филёнка и т.п. — деревянные/МДФ детали, которые нарезаются в
цехе и затем укутываются плёнкой). Сегодня система знает о деталях
только как о текстовом справочнике размеров (`Part`) для автоподсказки —
у самих заготовок нет ни остатков, ни местонахождения, ни статуса, ни
истории движения, в отличие от плёнки (`MaterialUnit`).

Уточнено с пользователем:
- Единица учёта — **партия/лот в штуках** (как `good_pieces` в
  `ProductionTaskLineReport`), а не поштучно-серийные записи, как у плёнки.
- **Нужны конкретные стеллажи/полки для п/ф**, как у плёнки (не просто
  «участок» текстом).
- **Нужен QR на саму партию** (этикетка на стопке/пачке) уже в первой
  версии — скан открывает карточку партии.
- Цвет/материал плёнки к п/ф не привязывается напрямую — виден через
  `ProductionTaskLine`, если партия сделана под задание; безадресный
  запас — без цвета вообще.
- Факт производства вводит **начальник цеха** (роль `nachalnik_tsekha`,
  id=4, уже существует, сейчас имеет только `orders.plan`/`reports.view`).
- Точные названия статусов/этапов оставлены на усмотрение реализации —
  предложенный набор ниже простой и легко расширяемый.

## Предлагаемые статусы п/ф

Так как п/ф — это то, что ЕЩЁ ПРЕДСТОИТ укутать (существует до/независимо
от плёнки), а не результат укутки, жизненный цикл партии короткий:

```
Нарезано → Выдано_участку (на укутку/сборку)
         ↘ Списано (брак, с любого этапа)
```

Без промежуточной «Готово» — она дублировала бы `Нарезано` (укутка уже
отслеживается существующим конвейером
`ProductionTaskLineReport`/`ProductionTaskLineAssignment`). Добавить
дополнительный этап позже — дешёвая правка (один новый член enum + одна
кнопка перехода), можно уточнить у цеха после первого использования.

## Решение по архитектуре хранения

**Отдельная таблица `PartRack`, не переиспользование `Rack`.** Причины:
1. `Rack`/`storage.py`/`StorageMap.tsx` — часть уже живой, ежедневно
   используемой системы учёта плёнки (проект в проде). Трогать её ради
   нового несвязанного домена — ненужный риск регресса. Рулоны/штрипсы
   плёнки и лоты п/ф считаются в корне по-разному (метры непрерывной
   длины vs штуки), так что `RackType`/`strip_capacity` всё равно
   пришлось бы городить условной веткой под другой смысл.
2. Полностью параллельная, но отдельная таблица даёт тот же UX
   (стеллаж → полка → сканирование), нулевой риск для плёнки, код —
   прямой перенос уже проверенного паттерна, а не хак поверх чужой
   модели.

У плёнки уже есть полезный прецедент — «виртуальные» стеллажи-накопители
без привязки к конкретной физической полке (`Резка`, `Орма`,
`Перемотка` — тип `STRIP`, `shelf_count=1`, `strip_capacity=999`, то есть
по сути именованные зоны цеха, а не пронумерованные полки). Так и для
п/ф — не тащить в неё полную геометрию складского стеллажа.

`backend/app/models/part_storage.py` (новый файл):
```python
class PartRack(Base):
    __tablename__ = "part_racks"
    id: Mapped[int] primary_key
    code: Mapped[str]                  # unique, напр. "ЗГ-1" (Заготовки)
    shelf_count: Mapped[int]           # обычно немного — именованные зоны цеха
    is_active: Mapped[bool] = True
```
Без `warehouse_id`/capacity-лимитов на первой версии — п/ф физически
живёт в одном цехе, между складами не путешествует; добавить позже —
дешёвая миграция, если появится реальный сценарий межскладского
перемещения п/ф.

## Модель данных

`backend/app/models/part_units.py` (новый файл) — зеркалит
`backend/app/models/units.py:27-93`, но лот, не серийная единица, и с
полкой на именованном стеллаже п/ф вместо ячейки складского стеллажа
плёнки:

```python
class PartUnitStatus(str, Enum):
    NAREZANO = "Нарезано"
    VYDANO_UCHASTKU = "Выдано_участку"
    SPISANO = "Списано"

class PartUnit(Base):
    __tablename__ = "part_units"
    id: Mapped[int] primary_key
    part_id: Mapped[int]                        # FK parts.id
    quantity_pieces: Mapped[float]               # Numeric(12,2)
    status: Mapped[PartUnitStatus]
    location_code: Mapped[str | None]            # "ЗГ-1-01" — на стеллаже п/ф
    area: Mapped[str | None]                      # FK areas.code — выдано участку (взаимоисключимо с location_code, как у MaterialUnit)
    production_task_line_id: Mapped[int | None]   # FK, ondelete=SET NULL, indexed; NULL = безадресный запас
    parent_id: Mapped[int | None]                 # FK part_units.id — дробление лота при частичной выдаче
    note: Mapped[str | None]
    created_by: Mapped[int]                       # FK users.id
    created_at / updated_at
```

`backend/app/models/part_events.py` — упрощённый аналог
`MaterialEvent`/`record_event` (`backend/app/services/events.py:9-26`):
```python
class PartEventType(str, Enum):
    PROIZVODSTVO = "Производство"
    RAZMESHCHENIE = "Размещение"       # на полку стеллажа п/ф
    VYDACHA_UCHASTKU = "Выдача_участку"
    SPISANIE = "Списание"

class PartUnitEvent(Base):
    __tablename__ = "part_unit_events"
    id, part_unit_id (FK), event_type, quantity_delta, from_cell/to_cell,
    area, production_task_line_id (снимок), user_id (FK), occurred_at, note
```

Частичная выдача — по образцу резки плёнки: у исходного лота
`quantity_pieces` уменьшается, создаётся новый `PartUnit` (`parent_id` =
исходный, статус `Выдано_участку`) + событие на каждой стороне.

## QR-коды

Два независимых носителя, оба — как у плёнки, просто закодированный
текст без JSON/URL (`backend/app/services/labels.py::qr_data_uri`,
переиспользуем ту же функцию):

- **Этикетка партии (`PartUnit`)** — QR = `"ПФ" + id` (напр. `"ПФ42"`).
  Префикс обязателен: голые цифры уже заняты `id` юнита плёнки в
  существующем сканере, коллизия была бы тихим багом.
- **Этикетка полки стеллажа п/ф** — QR = голый `location_code`
  (напр. `"ЗГ-1-01"`), тем же способом, что и `ShelfLabelData` у плёнки.
  Префикс `"ЗГ-"` не пересекается с существующими префиксами стеллажей
  плёнки (`Р-`/`Ш-`/именные).

Сканирование — расширить `frontend/src/utils/unitSearch.ts::
runUnitOrMaterialSearch` (аддитивно, старое поведение не трогаем):
- `^ПФ(\d+)$` → карточка партии п/ф.
- `^ЗГ-...` → новый экран стеллажей п/ф вместо `/storage`.
- Голые цифры / прочие формы — как сейчас.
